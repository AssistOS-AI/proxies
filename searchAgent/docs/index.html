SearchAgent Documentation

Purpose and interfaces

SearchAgent lets Ploinky agents and OpenAI-compatible clients run web searches without handling provider-specific request and response formats. A caller selects a provider, submits a query, and receives results with stable title, url, and snippet fields while any useful provider fields remain available.

The authenticated MCP interface exposes search_agent_search, search_agent_get_settings, and search_agent_update_settings. The bundled AgentServer also exposes /v1/chat/completions and /v1/models for integrations that use an OpenAI-compatible protocol.

Using MCP search

search_agent_search requires a provider and a non-empty query. maxResults is optional and cannot exceed the persisted service limit.

{
  "provider": "searxng",
  "query": "Ploinky agent routing",
  "maxResults": 5
}

A successful response identifies the selected provider and returns an array of normalized search results. Search-shaped failures return ok: false, a structured error, and an empty result array. SearchAgent trims input but does not semantically rewrite the query.

Using the OpenAI-compatible API

The Chat Completions handler treats request.model as the provider key and the latest non-empty user message as the query. It runs the same search behavior with a fixed request limit of ten results. The assistant message contains a JSON string with the query, provider, limit, status, and results. When stream is true, the handler emits that same JSON string in one Server-Sent Events text delta, emits a finish chunk, and ends with [DONE].

The Models handler lists only providers that are ready. Each provider appears as an OpenAI model with the search tag, search and retrieval capabilities, the active limits, and pricing metadata that distinguishes free providers from providers that require an external credential.

Providers and result normalization

The provider registry includes duckduckgo, tavily, brave, exa, serper, searxng, jina, gemini, deep-research, and google-ai-mode. Each adapter maps its response to the stable result fields. Entries without a URL are removed, duplicate URLs are collapsed, and the requested result limit is applied.

The deep-research provider queries configured API providers concurrently, skips unknown or unconfigured providers, tolerates individual failures, records the source provider, and deduplicates the combined results by URL.

Settings and credentials

SearchAgent persists only maxResults and maxQueryChars in $HOME/search-agent-settings.json. Their accepted ranges are 1–100 and 1–20000. The update tool normalizes both values and atomically replaces the settings file. Provider selection is request data and is not persisted.

Provider API keys are DPU secrets. The settings interface stores and grants them to agent:proxies/searchAgent, while search execution loads only the keys declared by the selected provider. JINA_API_KEY is optional; TAVILY_API_KEY, BRAVE_API_KEY, EXA_API_KEY, SERPER_API_KEY, and GEMINI_API_KEY are required for their corresponding providers.

Runtime and readiness

The manifest sets startup to manual. An operator or dependent agent must activate SearchAgent before use. Its startup script requires an installed local SearXNG, waits for the JSON search API on 127.0.0.1:8888, optionally starts the Google AI Mode browser pool, and then starts AgentServer on port 7000.

The readiness script requires both AgentServer and SearXNG to answer successfully. The browser pool is optional: when Chromium or puppeteer-core is unavailable or the sidecar fails to become ready, SearchAgent continues without advertising google-ai-mode as a ready model.

Operational boundaries

SearchAgent writes structured operational events to standard error so tool responses on standard output remain valid JSON. Logs include provider, input length, limit, duration, result count, and error classification, but omit raw queries, result text, URLs, and secrets by default. SEARCH_AGENT_LOGS=0 disables these logs.

Provider availability is evaluated at model-list time and again during execution. A listed provider can still fail because an upstream service changes after discovery. SearchAgent reports that failure through its structured error contract and does not promise semantic ranking consistency across providers.
