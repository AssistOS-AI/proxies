OpenCode Free Documentation

Purpose and interfaces

OpenCode Free makes OpenCode's zero-cost models available as plain-text chat models behind the local Soul Gateway. OpenCode serves its free tier only to its own client, so the agent runs the real, unmodified OpenCode CLI once per request inside its own container and returns the answer through the OpenAI-compatible /v1/chat/completions and /v1/models handlers of the bundled AgentServer.

Soul Gateway finds the agent through the Router's generic OpenAI agent discovery and offers its models as proxies/opencode-free/<model>. Soul Gateway contains no OpenCode-specific code, the agent has no path back to Soul Gateway, and the models join no Soul Gateway tier unless an administrator adds them.

What a request can and cannot do

A request carries text-only system, user and assistant messages ending with the user turn, for one of the seven allow-listed models. Tool calling, images and other non-text parts, n other than 1 and structured response formats are rejected with HTTP 400 before the CLI starts, so they cost no quota. Sampling parameters such as temperature and max_tokens are accepted and ignored.

The messages are joined into one flattened prompt with System instructions:, User: and Assistant: labels. The CLI returns the answer as one piece, so a streamed reply carries the whole answer in a single content delta after several seconds, preceded by keepalive comments while the CLI works. Each request also carries about 6,200 input tokens of tool definitions that OpenCode's service requires.

Confinement

OpenCode's service accepts a free-tier request only when the CLI's thirteen built-in tool definitions are part of it. The agent keeps them defined but never executable: its baked configuration answers every tool with ask, and the non-interactive run rejects every permission request. On top of that, the agent fails the request closed when the model attempted any tool, when the run finished for any reason other than a completed answer, or when any cost was reported, and it never returns text from such a run. A completed tool call or a reported cost also takes the agent out of service until the container restarts.

Service state and readiness

Ploinky readiness checks only local facts: AgentServer answers, the CLI binary matches the digest recorded in the image, the configuration is read-only, and the CLI resolves the agent's permission rules without contacting the service. Whether OpenCode's service actually answers is kept in a separate service state: a background probe sends one short request when the container starts and records verified, refused, unavailable or tripped in /data/service-state.json. Until the state is verified, chat requests are refused with an explained error before any CLI run and the model list is empty; a refused service is probed again after a day, an unavailable one with a back-off of up to an hour.

Errors

Every failure carries an HTTP status and a type that Soul Gateway classifies: 400 for invalid requests, 403 when OpenCode refuses the free tier, 404 only when the service reports that a model does not exist, 429 for rate limits and a full concurrency cap, 502 for confinement rejections and CLI failures, 503 while the service is not verified, and 504 when the 90-second CLI deadline passes. A refused or model-not-found request is not retried by Soul Gateway; the others may be.

Limits and data use

Each container runs at most two CLI processes at once. The free quota is shared by every installation that uses the bundled key, and it is not measured. Prompts are subject to the free models' data-use terms: free-period data may be used to improve the models, and some models are for trial use only and must not receive personal or confidential data. Do not send confidential prompts to these models.

Maintaining the model list

The allow-list is reviewed for one CLI version. When the pinned CLI changes, the maintainer lists the models the official CLI reports for the key with scripts/survey-models.sh and updates the allow-list, the manifest description and DS004 together.

Documentation authority

The wiki is the canonical terminology source. The specification matrix indexes the authoritative contracts. DS001 governs source layout and tests.
